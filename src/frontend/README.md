# Front end source code

This directory contains the two Angular portals.

## Apps

| Name           | Users                     | Angular | Node (Docker build image) | Backing API (host port) | Doc |
| -------------- | ------------------------- | ------- | ------------------------- | ----------------------- | --- |
| citizen-portal | Public disputants         | 16      | 18.12                     | citizen-api (5080)      | [README](citizen-portal/README.md) |
| staff-portal   | VTC staff and JJs         | 21      | 24                        | staff-api (5090)        | [README](staff-portal/README.md) |

Both portals use Yarn 1 (classic) and `yarn.lock`. The Dockerfiles run `yarn install`, so use Yarn rather than npm when changing dependencies. Use a Node version that matches the app's Docker build image. The two portals need different versions, so a version manager such as `nvm` helps.

- **Don't run `npm install` or `npm ci` in a portal folder.** npm rewrites `yarn.lock` whenever one exists, even with `--no-save`. If it happens, restore the file with `git checkout -- yarn.lock`.
- **Ignore `staff-portal/package-lock.json`.** It's a stale leftover that is missing newer dependencies, so `npm ci` fails against it.
- **If Yarn isn't installed globally,** run it through npx, for example `npx yarn@1.22.22 install --frozen-lockfile`. `--frozen-lockfile` installs exactly what `yarn.lock` lists and fails instead of changing it.

## Run locally

Start the backing API with docker-compose from the repository root (see the [root README](../../README.md#run-docker-compose)). Then, in the portal directory:

```bash
yarn install
yarn start
```

`yarn start` proxies `/api` to the backing API using `proxy.conf.json`.

| Portal         | `yarn start` serves on   | docker-compose serves on |
| -------------- | ------------------------ | ------------------------ |
| citizen-portal | http://localhost:5200    | http://localhost:8080    |
| staff-portal   | http://localhost:4200    | http://localhost:8090    |

## Build, lint, and test

Run these in the portal directory:

| Task | Command |
| ---- | ------- |
| Lint | `yarn lint` |
| Unit tests (headless, single run) | `yarn coverage` |
| Development build | `yarn build-dev` |
| Production build | `yarn build-prod` |
| Regenerate API client from a running API's Swagger | `yarn api:regenerate` |

In citizen-portal, `yarn test` starts Karma in watch mode, so use `yarn coverage` for a single run. In staff-portal, `yarn test` already runs once, headless. CI lints and tests citizen-portal (`.github/workflows/main-code-climate-coverage-aggregation.yml`) and builds its Docker image on pull requests (`.github/workflows/pr-frontend.yml`).

### Generated API clients (`src/app/api`)

`src/app/api` is generated by `openapi-generator` (`typescript-angular`) from the checked-in `src/app/api/swagger.json`. The `api:*` scripts download the Swagger from a running API, so a full regeneration needs that API running locally, and it can pull in unrelated changes if the checked-in Swagger is stale.

For a small model change, it's normal to edit `swagger.json` and the affected `model/*.ts` files by hand instead, copying what the generator produced for a similar existing property. TCVP-3443 (`occamDisputeCreatedBy`) and TCVP-3480 (`disputeSourceType`) were done this way. Enum members are PascalCase versions of the values, for example `Unknown: 'UNKNOWN'` and `Citz: 'CITZ'`. New model files must also be exported from `model/models.ts`.

## Troubleshooting

- **Dozens of `NG8001 '<element>' is not a known element` or `NG8002` errors** across unrelated components, usually after a `TS2307: Cannot find module '<package>'`, mean `node_modules` is stale. Reinstall with `yarn install --frozen-lockfile` and build again.

- ZScaler can interfere with opening the portals in a browser. Try disabling and re-enabling it.
- If a Docker build fails with "Call retries were exceeded" and exit code 127, increase Docker Desktop's memory limit.
