## Goal

The system used to work out where a dispute came from by looking at `ENT_USER_ID`. `'OCCAMORDS'` (the ORDS user the Workflow service connects as) meant a citizen submission; any other value was a staff user name. That stops now. Instead, the source is stored explicitly in the new `DISPUTE_SOURCE_TYPE_CD` column on `TCO.TCO_DISPUTES` and `OCCAM.OCCAM_DISPUTES`. The column is a foreign key to `TCO.TCO_DISPUTE_SOURCE_TYPES`:

| Code | Meaning |
|---|---|
| `CITZ` | Citizen Portal |
| `STAF` | Staff Portal |
| `JSTN` | JUSTIN (not used yet) |

The table, the columns and the backfill of existing rows are already in place. They are owned by another team; see [schema-ownership.md](../database/schema-ownership.md).

## How disputes are created

- **Citizen:** Citizen portal → `Workflow.Service` `SubmitNoticeOfDisputeConsumer` → `IOracleDataApiService.SaveDisputeAsync`.
- **Staff:** Staff portal → `Staff.Service` `DisputeService.CreateDisputeAsync` → the same `SaveDisputeAsync`.
- **Both then continue:** Java `oracle-data-api` `DisputeService.save` → `DisputeRepositoryImpl.saveAndFlush` → `ViolationTicketMapper` → ORDS `processViolationTicketPost` → `occam_rest.prProcessViolationTicket` → `occam_violation_ticket.pDisputeSave` → `INSERT OCCAM_DISPUTES`.
- **TCO_DISPUTES:** these rows are **not** created through any API. A JUSTIN appearance trigger calls `tco_appearance_data_modify.prCreateDispute`, which reads the matching OCCAM_DISPUTES row and calls `tco_dispute.pDisputeSave`.

## Decisions

- **The source is a JSON field, `disputeSourceTypeCd`.** No ORDS handler changes are needed.
  - **Why:** the handlers pass `:body_text` straight to PL/SQL.
- **The services set the source, not the browser.**
  - Workflow.Service sets `CITZ`.
  - Staff.Service always sets `STAF`, ignoring anything the client sent.
  - **Why:** a browser could otherwise claim any source.
- **The source never changes after insert.** Update procedures and update code paths must not overwrite it.
- **TCO copies the source from OCCAM** inside `prCreateDispute`.
  - **Why:** no caller is involved when that row is created.
- **Temporary fallback in OCCAM `pDisputeSave`:** when no source is passed, it uses `CITZ` if `NVL(pEntUserId, USER) = 'OCCAMORDS'`, otherwise `STAF`.
  - **Why:** the packages can be deployed before the application changes without mislabelling disputes.
  - **Remove it in a later release**, once every caller sends a source.
- **Staff portal display text:**
  - `CITZ`: "Disputant"
  - `STAF`: `STAFF (<ENT_USER_ID>)`, for example `STAFF (DAVEKAY)`
  - `JSTN`: "JUSTIN"
  - The first-person versus third-person wording in `jj-count` switches on `disputeSourceTypeCd === 'CITZ'`.

## Done: Phase 3, Java oracle-data-api (uncommitted, branch `fix/tcvp-3480`)

- **OpenAPI specs:** `disputeSourceTypeCd` (nullable string) is added to the `Dispute` schema in `occm-openapi-spec.yaml` and the `JJDispute` schema in `tco-openapi-spec.yaml`. The ORDS clients are generated from these at build time.
- **Model:** a new enum `model/DisputeSourceType.java` (`UNKNOWN`, `CITZ`, `STAF`, `JSTN`). `UNKNOWN` comes first, following the project's index-0 convention. A `disputeSourceType` field is added to `Dispute.java` and `JJDispute.java`, using the same plain-enum pattern as `signatoryType`.
- **Mappers:**
  - `ViolationTicketMapper` sends the enum name through `@Named("mapDisputeSourceType")`, which turns `UNKNOWN` or null into null. Null lets the DB fallback decide, and `UNKNOWN` would fail the foreign key.
  - `DisputeMapper` and `JJDisputeMapper` (the ORDS → model direction) map the code to the enum.
  - The reverse `JJDisputeMapper` (model → ORDS, used for updates) ignores `disputeSourceTypeCd`.
- **`DisputeService.update`:** `disputeSourceType` is added to the `BeanUtils.copyProperties` ignore list.
- **Tests:**
  - `DisputeMapperTest`: code → enum, and null → null.
  - `ViolationTicketMapperTest`: each code passes through, and `UNKNOWN` and null become null.
  - `JJDisputeMapperTest`: asserts the new field.
- **Test run (2026-10-14):** `./mvnw test` with JDK 21 ran 162 tests across the mapper and dispute service tests. All pass except 2 failures in `DisputeServiceImplTest` (`testUnassignExpect200`, `testUnassignExpect500_ApiException`, "Invalid ResponseResult object"). Those 2 also fail on unmodified `HEAD`, so they are pre-existing and unrelated.

The Java API now **accepts** `disputeSourceType` on create and **returns** it on Dispute and JJDispute. Nothing sets it yet; that's Phase 4.
